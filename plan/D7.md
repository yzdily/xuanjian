# 2. D17 · mitmproxy 18080 根因（需完整环境复现）

## 2.1 启动链源码实读（`start.py`）

启动入口 `start_mitmproxy()`（:459），关键链路与**已浮现的缺陷**：

| 行号 | 代码事实 | 问题 |
|---|---|---|
| 344–346 | `is_port_in_use(port)` 仅 `connect_ex(("127.0.0.1", port))==0` | 只查 TCP 端口占用，**不验证监听者是否为 mitmproxy** |
| 349–360 | `_is_mitmproxy_port(port)` 发 `GET http://mitmproxy-check/` 看响应含 "mitmproxy"/"Proxy"/"502" | 真正的代理探测，**但仅被 `check_ports` 复用逻辑调用，未被 `start_mitmproxy` 健康检查使用** |
| 363–383 | `check_ports()`：端口被占用且 `_is_mitmproxy_port` 为真 → "复用现有实例" | **陈旧实例泄漏复用**：旧 mitmproxy 未退出仍绑 18080 时，新进程"复用"它，但… |
| 464–465 | `FLOW_FILE.write_text("")` 每次启动**先截断流量文件** | …新运行截断 FLOW_FILE，而陈旧实例写的是**它自己启动时**的 FLOW_FILE 路径（env 注入的 `PROXY_FLOW_FILE`），两者不一致 → **流量落盘错位/缺失** |
| 475–546 | `mitmdump_path` 候选 5 处（sys.executable 同级 / Scripts / macOS framework / sysconfig / conda / ~/.local）+ 最后 `python -c from mitmproxy.tools.main import mitmdump` 兜底 | 路径未命中时静默降级；依赖缺失仅 warn 不报错 |
| 553–564 | `Popen` + `stderr=PIPE` + 后台 daemon 线程 `_drain_mitm_stderr` | Windows `creationflags=CREATE_NEW_PROCESS_GROUP`（:556）→ 父进程退出时子 mitmproxy **不被回收**，泄漏 |
| 402 / 418 | `_mitm_stderr_lines` 仅内存存前 50 行 | **进程退出即丢**，无法复盘根因 |
| 570–579 | 健康检查轮询：仅 `is_port_in_use(PROXY_PORT)` 为真即 `proxy_ok=True` | **弱健康检查**：任何进程绑 18080 都报"已启动并验证可用"；若绑的是非 mitmproxy 进程则假成功 |
| 581–613 | 启动失败各分支 → "将以直连模式运行（无流量抓包）" | **三级降级静默吞错**：日志"端口 18080 仍未恢复"实为根本没起来，却只 warn 不 fail |

**降级/重启逻辑（运行时）**：`core/parallel/_orchestrator_helpers.py` 的 `_check_mitmproxy_health`(:34) / `_try_restart_mitmproxy`(:52) 被 `chat_loop.py:962-963` 调用，是运行时三级降级的执行点——它们能续命但**不解决根因**。

## 2.3 5 步定位法（master plan D17 锚点）

① 依赖缺失 → `mitmdump_path` 5 候选(:475-499) 是否命中，未命中走 `python -c from mitmproxy.tools.main import mitmdump`(:537-546) 验证包真装；② CA 证书 → `~/.mitmproxy/mitmproxy-ca-cert.pem` 首生成(:449 提示)，Win 需手动信任；③ 端口占用 → `check_ports`(:363)+`_is_mitmproxy_port`(:349) 复用旧实例(:370-372)；④ stderr 落盘 → `_drain_mitm_stderr`(:405) 收前 50 行，建议写 `data/logs/mitm_stderr_<ts>.log`(:418 当前仅内存)；⑤ 终极 → 容器化 mitmproxy（独立 service + healthcheck + supervisor）。

## 2.4 根因假设排序（按概率）

1. **陈旧实例泄漏复用**（最可能）：Windows `CREATE_NEW_PROCESS_GROUP` + daemon 线程使父退出不回收子 mitmproxy；第二轮 `check_ports` "复用"陈旧实例，但 FLOW_FILE 已被新进程截断 → 流量落盘错位，表现"18080 仍未恢复/无流量"。
2. **弱健康检查误报成功**：`is_port_in_use` 仅查端口，非 mitmproxy 进程绑 18080 也报绿；或 mitmproxy 起了但 addon 加载失败静默退出（exit_code==1 无 stderr，:452-454），实际代理不可用。
3. **mitmproxy 依赖/路径未命中**：5 候选全 miss 且 `importlib.import_module("mitmproxy")` 失败 → 直连降级（:533-536），端口当然不恢复。
4. **addon 脚本异常**：`mcp_servers/mitm_addon.py` 加载失败（见 `_print_mitmproxy_diagnosis` :453），进程启动即退。

## 2.5 修复方向（待复现确认后实施，本方案不给最终补丁）

- **健康检查升级**：`start_mitmproxy` 轮询(:570-579)改用 `_is_mitmproxy_port`（:349）真正探测代理响应，而非仅 `is_port_in_use`；探测失败即进入失败分支而非假成功。
- **进程生命周期**：启动前先按端口 `kill` 同端口陈旧 mitmproxy 实例（避免复用错实例）；`cleanup`(:423) 用进程组 `os.kill(pid, signal.CTRL_BREAK_EVENT)`（Win）确保子进程回收；考虑 `start_new_session=True` 替代 `CREATE_NEW_PROCESS_GROUP`。
- **stderr 持久化**：`_drain_mitm_stderr` 写 `data/logs/mitm_stderr_<ts>.log`（当前 :418 仅内存 50 行，进程退出即丢），供下次扫描前复盘。
- **终极方案**：容器化 mitmproxy（独立 service + healthcheck + supervisor），与运维 O7 协同——彻底解耦进程生命周期与父进程。

## 3.2 问题定性与收敛策略

- **改动性质**：纯机械重构，**零行为变更**。状态从"模块裸全局"移到"模块持有的不可变 `_state` 对象上的可变属性"——`global` 关键字随之消失，运行时语义、`reset_singletons` 行为完全一致。
- **为何不一步上中央 Container**：把 25 单例收进 `core/di.py` 中央 `Container` 需改所有调用点（爆破面大）。D7 目标是"降 `global` 计数 + 解锁并行单测"，**最小风险路径是每模块本地 `_state` 持有对象**。中央 Container 作后续可选演进，不在本方案范围。
- **分类**：

| 类别 | 变量（去重） | 语义 | 模式 |
|---|---|---|---|
| **A 懒加载进程缓存** | `_client`、`_CACHE`(auth/memory)、`_generator`(compliance/poc)、`_http_client`(fuzz/base·concurrent)、`_conn`、`_registry`、`_router`、`_fp_manager`、`_global_receiver`、`_SECRET_KEY`、`_ddddocr_cls`、`_ddddocr_slide`、`_rapidocr_inst` | 进程级单例/缓存 | `_state.X` 懒加载，resetter 置 None |
| **B 事件循环绑定原语** | `_queue`、`_semaphore`、`_worker_task`（task_queue，loop 绑定）+ `_pool`、`_concurrent`（task_queue 配置，由 `init()` 赋值） | 须绑运行中事件循环；`init()` 仅赋配置不建原语 | `_state` 承接，保留"首次调用才构造"语义，不得提前到 import 期 |
| **C 附加开关** | `_attached`（crypto_replay/register、diff/register、replay/register 三处同名但模块隔离） | 布尔"是否已 attach addon" | `_state.attached` 布尔，resetter 置初值 |

## 3.4 机械改造模板（before / after）

以 `core/asset_mapping.py` 为例（#1，模式 A）：

**Before**
```python
_client: AssetMappingClient | None = None

def get_mapping_client() -> AssetMappingClient:
    global _client
    if _client is None:
        _client = AssetMappingClient()
    return _client

def _reset_core_asset_mapping__client() -> None:
    global _client
    _client = None

register_resetter("core_asset_mapping__client", _reset_core_asset_mapping__client)
```

**After**
```python
from dataclasses import dataclass

@dataclass
class _AssetMappingState:
    client: AssetMappingClient | None = None

_state = _AssetMappingState()

def get_mapping_client() -> AssetMappingClient:
    if _state.client is None:
        _state.client = AssetMappingClient()
    return _state.client

def _reset_core_asset_mapping__client() -> None:
    _state.client = None

register_resetter("core_asset_mapping__client", _reset_core_asset_mapping__client)  # 行为不变
```

要点：`_state` 是不可变模块绑定，状态移到其属性 → 无 `global`；`register_resetter` 调用**原样保留**，仅内部 `global X`→`_state.X`；调用点零改动。B 类（`task_queue`）保留 loop 绑定语义（仍"首次在运行 loop 内才构造"，仅变量承载方式换）。D 类（`_PROCESS_RUN_ID`）保留 + 标注 + CI 白名单。
